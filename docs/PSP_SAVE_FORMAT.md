# PSP persistent-file and snapshot envelopes

The native PSP package declares `ppsspp-files-opsf2` for in-game saves and the corresponding pin-specific `opns2-fs2-native64` snapshot identity. These are private OmniPlay envelopes over the user's files, not a claim that the bytes are a PSP memory-card image or a universal emulator snapshot. Saves retain the exact immutable game-content hash and normal generation/parent/conflict metadata.

All integers are unsigned 32-bit little endian. `OPSF0002` is eight ASCII magic bytes followed by an entry count. Each entry has a kind (0=file, 1=directory), UTF-8 name byte count, payload byte count, name bytes, then payload. A directory must have zero payload bytes. A zero-byte file remains a file. The root directory is implicit. Capture sorts paths by their UTF-8 bytes. Readers accept any entry order after full validation, create implicit parents, and reject duplicate names and a file used as any entry's parent. There is no compression, executable extraction, alternate-stream syntax or renderer-selected output path.

The complete envelope is limited to 256 MiB, 8,192 materialized entries including implicit parents, and 4,096 regular files. A path is at most 512 UTF-8 bytes, eight components and 255 bytes per component. Empty components, absolute paths, dot segments, backslashes, control characters, Windows reserved punctuation, trailing dots/spaces and reserved devices are invalid. Windows filename equivalence uses strict UTF-8 decoding and invariant Unicode case mapping; exclusive creation is the final filesystem collision check. Reparse points and non-regular entries are rejected before traversal or cleanup. These restrictions deliberately bound this Windows adapter; other platform policies still require implementation and qualification.

The v2 reader also accepts `OPSF0001`: magic, file count, then name byte count, payload byte count, UTF-8 name and file payload for each entry. V1 has no directory kind field and no representation for empty directories. Its 4,096-file count and the common materialized-entry/path/byte limits apply. Compatibility explicitly allows `ppsspp-files-opsf1` to a target declaring the v2 portable in-game reader. The reverse direction and any arbitrary version-prefix relation remain incompatible. This relation never permits an opaque snapshot to cross core, build, backend, platform or configuration identities.

`OPNS0002` has magic, disc-index sentinel `0xffffffff`, zero disc flags, core-state byte count, archive byte count, then exact core-state bytes and the file envelope. The combined wire payload remains bounded at 256 MiB. Restore fully parses the envelope before mutation and captures prior raw core state and prior files separately, so a valid in-game restore does not fail merely because a combined rollback snapshot exceeds the wire limit. Each individual rollback capture remains bounded.

The guest is paused through its selected core barrier, asynchronous file I/O is drained, and snapshot APIs leave the guest paused. The worker closes guest/VFS handles, stages files in an owned sibling directory, flushes each Windows file and renames the directory into place. Reinitialization and state load must complete synchronously. Failure restores the prior files and guest state; failure of that rollback is fatal to the contained job. Only a later frontend resume can restart execution.

Directory replacement is a process-level recovery transaction, not a verified power-loss transaction across two directory renames. Live disk-write quotas, handle-relative hardening against a hostile contained background thread, power-loss recovery, alias edge cases and other-platform filenames remain required containment/verification work. No codec, filesystem, emulator or recovery test has run.
