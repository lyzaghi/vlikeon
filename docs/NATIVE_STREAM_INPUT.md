# Owned-game native keyboard/mouse source

The newer `OWNED_NATIVE_CAPTURE.md` source adds Windows capture-process and exact
captured-window correspondence. Input now requires the broker's capture UUID
and the component worker's private HWND binding; generic browser capture cannot
arm this path. Patch/build/device execution remains deferred.

This is authored Windows source and is disabled by the installed product policy. The helper build recipe has not been invoked. No process, native dialog, input event, game, device or test has run. This document does not establish a containment, input-delivery or release-readiness result.

## Authority and target selection

The Game Hub can request native control only when the compiled broker policy enables streaming, browser hosting and remote input for explicitly configured HTTPS relay origins. The broker also needs an installed helper admitted by the running broker's signed release inventory. There is no renderer-selected helper path, command line, PID, window handle, environment override, shell, elevation request or driver install. The default policy remains disabled with no relay origins.

Pairing can include permission to request keyboard/mouse only when that native capability is present. A paired input permission does not arm a game. The local host separately selects a running PC game and approves a native dialog naming that library game and the peer fingerprint. The broker verifies the host-signed grant, exact pair identity, enabled audience, input permission and certificate lifetime. This source still relies on the authenticated Game Hub session for the correspondence between its browser-held host key and the local UI context; native pairing-key custody and independent native relay-revocation confirmation remain required work.

Targets come only from `InstalledGames` child handles retained by this broker. The renderer receives library/session/capability UUIDs, never a process identity. A safe duplicated process handle supplies the PID and creation time; the helper opens and checks that exact identity before any input. A launcher that creates a different game process is not silently expanded into arbitrary descendants or another window. Launcher integration and other game-host process models remain required, explicit product work.

The broker repeats lifetime/process checks after local consent, enforces the original request deadline after both the dialog and helper setup, and issues an unpredictable input grant bound to game, pair and remote session. Its maximum duration is the lesser of remaining pairing-certificate validity and thirty minutes. The child receives the absolute local expiry and derives its own monotonic budget after startup, so startup does not extend authority. Input commands and capability responses bypass the native request-result cache. Audit records contain the selected game UUID and authorization event, not typed input or paths.

## Independent helper and watchdog

`platform/stream-input` contains the private client, protocol, helper main loop and Windows FFI. The helper is a trusted normal-user component, separate from the untrusted emulator AppContainer. It needs ordinary desktop input authority and is not presented as an AppContainer-isolated injector. It receives a cleared environment with only Windows system paths, fixed `--stdio-input-v1` mode and private stdio. No network listener or runtime core/plugin is loaded.

The protocol uses schema/version 1, correlated increasing request IDs, fixed grant/session UUIDs and at most 16 KiB of JSON per frame. A bounded reader queue prevents an unbounded stdin backlog. Invalid framing, identity, state or schema ends the owned helper path. The main loop checks liveness at roughly eight-millisecond intervals independent of the broker's control loop. EOF on its private owner pipe causes release/exit when the broker disappears; this behavior is authored, not fault-tested.

The game has thirty seconds to bring the exact captured window to the foreground and allow a 250 ms quiet period for the local activation click/key to settle. The helper then latches that authorized window. Process exit, target-window loss/minimization, grant expiry or detected F12/Ctrl/Alt/Windows state revokes the grant. A 250 ms input gap releases tracked keys/buttons without inventing new input. Game Hub coalesces unsent frames and accumulates bounded relative motion rather than forwarding a stale queue. Other native dialogs or a blocked broker cannot suspend the helper's own input-gap/focus checks. Native result failures close the helper/capability path.

The helper tracks possibly inserted downs before an OS batch, releases the prior/next union if insertion is partial, and reports blocked/release failures. Release failure retains tracked state for retry. Normal stop, owner loss and Drop attempt held-state cleanup before exit. A stalled/killed helper, UIPI restriction, secure-desktop transition, kernel/desktop failure or process termination can defeat a user-space cleanup attempt; the source does not claim a guaranteed OS key reset under all failures. Independent fault evidence and a release-safe failure strategy remain mandatory before enabling this path.

## Input and Windows boundary

The shared codec bounds a unique set of at most 32 allowed physical key codes, relative mouse/wheel values and button bits, plus a declared gamepad shape. Windows maps the admitted physical keys to scan codes and uses the target thread's keyboard layout when checking pre-existing key state. Windows/Alt/Ctrl/function-key injection, arbitrary virtual-key values, Unicode text injection and shell shortcuts are not accepted by this codec. A dedicated message-pumping thread installs low-level keyboard/mouse hooks, records only an activity counter/time and ignores this helper’s own tagged injected events. After activation, any other observed keyboard/mouse event revokes the grant; no key values, text or event history are stored. A stale observer heartbeat also revokes. Per-process event tags provide attribution, not a secret authentication boundary. Windows can silently remove a low-level hook after callback timeout, and this source cannot prove continuous hook coverage through its own heartbeat alone. Raw-input integration, game cursor-warp behavior, other input producers and actual local arbitration still require qualification and any necessary stronger implementation before release. See the [keyboard hook contract](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc) and [mouse hook contract](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc).

The source uses the [Microsoft SendInput API](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput), which targets the system input stream and is subject to UIPI. Foreground identity is checked through [GetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getforegroundwindow) and [GetWindowThreadProcessId](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowthreadprocessid), including a final check before insertion. Those calls and the actual input insertion are not one atomic Windows transaction. Focus/desktop changes between checks are an unresolved release gate; the source must not be described as proof that an event can never reach another UI surface.

Pointer work requires per-monitor DPI awareness, a live target client rectangle, the current pointer within that rectangle and a matching root window under the pointer. Movement is bounded and converted to absolute virtual-desktop coordinates inside that client area, avoiding unbounded desktop movement. It does not claim raw relative-mouse/FPS-game equivalence. Multiple monitors, DPI transitions, overlays, cursor capture, unusual window hierarchies, keyboard layouts and actual game compatibility remain unverified. Generic browser screen selection remains separate. The newer owned Windows path binds the selected native capture window to the input helper; other host adapters remain required.

Virtual gamepads are explicitly unavailable in this helper. A nonneutral unsupported gamepad frame revokes rather than silently remapping to arbitrary keys; the negotiated current client policy omits gamepad input and labels keyboard/mouse availability. The receiving Game Hub now authors a local touch overlay mapped explicitly to the existing keyboard/mouse permission, plus v2 data-channel epochs and release fences. The native forwarder serializes pending release/frame calls and coalesces bounded pending work. See `REMOTE_TOUCH_AND_INPUT_FENCES.md`; actual touch/device/ordering behavior is unverified. Signed virtual-device/platform integration, haptics and native capture/encoding remain required scope.

## Lifecycle, packaging and evidence

The extension tracks native input capabilities by originating page, including a late grant response after page closure/timeout, and sends revocation for abandoned grants. Closing the stream/page disarms the RTC input policy and revokes the native grant; broker teardown also closes its helper owner pipe. Other tabs cannot use an unknown UUID capability through this API. Exact late-response, owner-loss, replay, timeout and held-key behavior still require the final fault pass.

`tools/build_stream_input.py` authors the explicit later Windows x64/ARM64 Cargo build and staging recipe with a fixed helper path, static CRT request, PE mitigation linker options and source/lock/artifact receipt. It does not execute the helper or a test and has not itself been run. A built receipt alone will not admit execution: the complete release inventory, entry verification, notices/source offer, platform qualification and all final security checks remain required.

The final consolidated pass must include cross-language frame validation, process reuse/exit, modal deadlines, foreground and pointer races, local override, client blur/release, broker/helper termination, stalled/malformed pipes, partial insertion and cleanup failure, secure desktop/UIPI, real target games/input devices and the unimplemented full host/platform paths. Native input, the streaming epic and the full OmniPlay product remain incomplete.
