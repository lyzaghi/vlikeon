# Remote-play source protocol and boundaries

This is authored source for a portion of the full v1 remote-play pipeline. The product configuration is disabled and contains no active relay origin. No signaling service, TURN deployment, browser capture, peer connection, input injection, codec, mobile device or test has been run. Files and source assembly do not establish that authentication, performance, codecs or containment work.

## Components and trust

`platform/streaming` defines and verifies Rust wire documents. `services/signaling` is a loopback HTTP upstream intended for a configured TLS ingress. `engines/streaming` implements the shared browser cryptography, pairing store, signaling transport, WebRTC media, bounded input frames and QoS policy. Game Hub's remote-play panel connects those sources through an explicit installed product policy. The Web/PWA, desktop and mobile assemblers copy the same inventoried modules and disabled configuration. Native installed-game launch remains a separate existing user-consented action; remote viewing does not silently launch or inject into a PC game.

The peer identity is an Ed25519 key generated by WebCrypto with a nonextractable private half. A persisted identity must prove possession of its public half before use. Browser IndexedDB stores structured CryptoKey objects, never raw private identity or pair keys in a JSON preference. This is origin isolation, not an OS key-vault, hardware-backed or resistance-to-origin-compromise claim. Native credential storage/bridging and stable mobile-origin persistence remain required. In particular, a temporary loopback origin or a nonpersistent WebKit data store does not supply durable pairing across app restarts.

The signaling service can observe endpoint identities, timing, pairing labels and ciphertext sizes and can deny service. Invitation secrets pass over the chosen TLS relay while enrolling a request; the service stores only their hash. The invitation pins the host identity, a client request is signed by the client, and the user must compare the displayed code on both devices before the host signs a grant. A malicious relay cannot authorize an arbitrary peer without that local approval, but comparison-code deception and origin compromise remain threat-model/verification cases. The six-digit code is a human comparison aid, not the secret used for encryption or a rate-unlimited standalone password.

The chosen APIs and media boundaries follow the primary [Web Cryptography](https://www.w3.org/TR/webcrypto/), [WebRTC](https://www.w3.org/TR/webrtc/) and [Screen Capture](https://www.w3.org/TR/screen-capture/) specifications. These references informed source authoring; they do not verify this implementation or establish every browser's support.

## Signed documents and pairing

A signed document has exactly `payload` and `signature`, both canonical unpadded base64url. The payload is the exact UTF-8 JSON byte string that was signed. Verification does not reconstruct or reorder that JSON. The signature covers the ASCII domain including its terminating NUL followed by the payload bytes. The domains are `omniplay.streaming.request.v1`, `.invite.v1`, `.hello.v1` and `.grant.v1` with the common `omniplay.streaming` prefix. Ed25519 public keys are 32 bytes and signatures 64 bytes; Rust rejects weak public keys and uses strict verification. Schema and unknown-field validation apply after signature verification.

Relay requests include schema 1, an exact configured HTTPS origin as audience, issued time, fresh UUID nonce and a tagged operation. The body must be within two minutes of service time. Consumed signed nonces remain in SQLite for four minutes. Exact request payloads are bounded at 96 KiB and HTTP bodies at 192 KiB. The server's errors omit user strings and paths. Origin policy supplements signatures; it does not replace authentication. Clock movement, retries, malformed/duplicate JSON and signature interoperability remain final-verification cases.

An invitation has a UUID, host public key, bounded label, SHA-256 hash of a random 32-byte secret, exact relay audience and at most five-minute validity. The copied `OPRP1.` invitation includes the signed descriptor and secret; it is not put into an HTTP URL, request query or service log. A join has a client-signed public identity, P-256 uncompressed exchange point, random nonce and label. At most eight joins can wait on an invitation. Local host approval binds the exact client hello hash and exchange/nonce values into a host-signed pair grant. The grant lasts at most ninety days and names both endpoints, both exchange keys/nonces, invitation, pair UUID, audience and input permission.

Both endpoints derive 256 bits through WebCrypto P-256 ECDH, import that material into HKDF-SHA256, use the hash of the ordered signed grant wrapper as salt and `omniplay.streaming.signal-key.v1` as info, and derive a nonextractable AES-256-GCM key. Temporary raw shared-secret bytes are cleared. The AES-GCM key is retained with its exact grant and endpoint role in the pairing store. Approval persists the key before sending its grant; unconfirmed approvals have an explicit retry path that can detect an already registered grant. Client collection is idempotent for the same signed authorization. These transitions have not been exercised.

Either endpoint can revoke the pair. Local revocation removes its CryptoKey reference and receiver lease first; a failed relay operation remains an explicit pending revocation with a retry control. The relay retains the revoked pair row until its certificate expires and rejects subsequent send/receive/ICE authorization. Local deletion, relay acknowledgement, other-tab polling and backing-store erasure are distinct; browser backups or a previously compromised endpoint are not erased by a protocol call.

## Encrypted signaling and relay bounds

Every signal has a random message UUID, session UUID, monotonic per-sender pair sequence, expiry within sixty seconds, random 96-bit IV and AES-GCM ciphertext. The authenticated data is the UTF-8 JSON array `["omniplay.streaming.signal.v1", pair_id, sender_public_key, message_id, session_id, sequence, expires_at_ms]`. Plaintext is at most 48 KiB minus the tag. A receiver validates peer identity, timestamps, IV/length, AEAD tag, local receiver ownership and advancing cursor/sequence before dispatch. Strict IndexedDB transactions reserve send sequences and advance receive state across tabs. A lease prevents two active receiving windows on the same endpoint/pair. Pair sequence is bounded at one million before renewal.

The relay verifies the registered exact host-signed grant and endpoint signature for every operation. A send retries the same message identity and bytes with fresh signed request nonces; a conflicting reuse is rejected. SQLite stores ciphertext without a content-decryption key. It bounds invitation count at 512, pair rows at 10,000, open invitations per host at two, active pairs per approving endpoint at 32, and queued packets at 256 per pair/4,096 total. Receive returns at most eight packets. Expiry cleanup and relevant indexes are authored. Logical row/packet caps do not replace filesystem quotas, ingress abuse controls, operational monitoring or physical storage qualification.

The relay also has bounded request concurrency, body size, global pre-verification rate limits and separate authenticated identity rates. Unauthenticated requests cannot consume another named identity's authenticated bucket. There is no public account service or externally deployed relay in this workflow. The self-hosted enrollment/abuse/deployment model remains subject to the complete product release review.

## Media, capture, input and QoS

The client is the sole SDP offerer. The host waits for an authenticated request and a local user gesture, then starts an owned capture request. The component extension can show Chromium's window picker and consume its local one-use desktop source token; the alternate path uses the normal getDisplayMedia picker. Audio is separately opt-in and governed by the chooser. Track configuration, cancellation/late results, local preview and stopping follow `REMOTE_CAPTURE_AND_CODECS.md`. Native owned-game target binding, independent capture/encoding and platform-specific audio paths remain required. Locally advertised codec preferences reorder browser capability objects while preserving negotiation fallback; H.264/HEVC/AV1 or hardware acceleration are not claimed from an API existing. Actual browser negotiation and the full codec/device matrix remain unverified.

Encrypted SDP must contain bounded SHA-256 DTLS fingerprints before it is supplied to WebRTC. Candidate queues, generations and pending negotiation are bounded; local ICE messages are held until the corresponding description is sent. The source includes a 45-second negotiation deadline, client-driven ICE restart with renewed credentials, bounded reconnect attempts and session-specific stop. Capture tracks/peer connections stop locally before a best-effort closing signal; a failed relay cannot hold the local capture sink open indefinitely. Signal transport failure and local revocation close the media session rather than silently retaining an unauthenticated continuation.

Authorized ICE credentials are issued only for a registered, unrevoked grant. The optional TURN service uses a ten-minute maximum timestamp username and the [coturn TURN REST HMAC-SHA1 credential construction](https://github.com/coturn/coturn/blob/master/README.turnserver); the long-term shared secret stays in server memory with zeroizing storage. This HMAC is the TURN authorization mechanism, not the signal encryption primitive. The client can require relay-only candidate policy. Missing TURN configuration reports relay unavailable; it is not presented as working NAT traversal. Ingress/TURN provisioning, renewal behavior and real LAN/WAN/relay coverage remain required.

Profiles request 720p/1080p at 30/60 FPS with bounded sender bitrate. Quality source reads actual WebRTC stats when available: nominated-pair RTT, video jitter, interval packet loss, decode time, jitter-buffer delay, decoded rate and dropped frames. Unknown counters stay null. Values follow the [WebRTC statistics definitions](https://www.w3.org/TR/webrtc-stats/). A host bitrate controller uses multiple bad/healthy windows, bounds, cooldown and a regression rollback; it does not alter guest emulation speed. There is no measured latency, battery gain, codec pass rate or controlled quality result.

Reliable control (`omniplay-control-v2` / `omniplay.control.v2`) and unordered zero-retransmit input (`omniplay-input-v2` / `omniplay.input.v2`) have size limits and session identities. Host epochs fence reauthorization; one client sequence space covers input frames and reliable release fences, rejecting delayed pre-release input. Input requires both signed permission and a separate live host policy. Focus/visibility/lifecycle loss clears held state. A host input gap after received frames disarms and revokes the native grant. Viewing-only pairing remains the default; the optional Windows owned-game path requires separate native consent and target checks. The receiving UI adds explicit local touch mapped to that same keyboard/mouse permission, with per-pair finite preferences. Gamepads stay unavailable and are not silently remapped. Both endpoints must support data channel v2; pairing/signaling/native helper versions are unchanged. See `REMOTE_TOUCH_AND_INPUT_FENCES.md` and `NATIVE_STREAM_INPUT.md`. Sending a validated data frame is not proof of OS input delivery.

## Remaining completion evidence

Full streaming completion still requires native host capture/encode and installed-game integration, explicitly consented target-bound input, persistent native/mobile credentials, store/lifecycle/audio integration, codec and TURN infrastructure, hardware capability selection, real reconnect/fault/revocation behavior, security/fuzz/cross-language cryptographic verification and controlled LAN/WAN input-to-photon evidence. All of that remains in the active full product scope. The authored service and client must participate in the one final consolidated verification after implementation is complete.

An additional Windows owned-game keyboard/mouse source path is now integrated behind the disabled native product policy. It has local native consent, signed permission checks, a separately inventoried helper, private IPC, independent liveness/input watchdog, foreground/process identity checks and page/stream revocation. The client input policy distinguishes keyboard/mouse from unavailable virtual gamepads. `NATIVE_STREAM_INPUT.md` defines the limits, including non-atomic SendInput/foreground behavior, incomplete physical-input arbitration, cleanup failures and the remaining native capture/device work. The preceding viewing-only behavior remains the default; this source addition is not permission to enable or release the unverified input path.
