# N64 native source integration

The selected source is Mupen64Plus-Next at `12edd2c74a517ff86dfa8cfc71ad75e4c10486d5`. `tools/build_mupen64plus.py --prepare-only` authors an adapted corresponding-source tree. It does not configure, compile, launch or verify an emulator. The explicit later build targets Windows x86-64; Android/iOS, GPU and dynamic-code adapters remain separate product work.

The initial signed configuration selects the pure R4300 interpreter, CXD4 RSP interpreter and Angrylion software RDP. Parallel backends and CPU dynarec are excluded by build flags. Windows coroutine dispatch uses OS fibers, and cached-instruction allocations are non-executable. GLideN64 code is still an upstream build input but is unselected; this is not a claim that its source or dependencies were removed. The existing contained worker keeps its network-denied AppContainer, no executable heap, memory/job bounds and private per-session files.

Core configuration and generated INI data use the explicit private `scratch` directory, which the broker creates and grants to that game container at low integrity. Core startup failure requests shutdown and is rejected before Ready. OS fibers preserve floating-point state when switching between guest execution and the host. These adaptations have source-preparation evidence only.

The library exposes controller-pak, cartridge SRAM, EEPROM and flash save memory through its upstream save-memory structure. OmniPlay preserves that opaque image in its exact-version memory envelope. Four controller ports use memory paks. Restoring persistent memory requests a guest reset after the copy, avoiding stale guest caches after a prior snapshot attempt. Before guest initialization the adapted reset is a no-op. No claim of cross-core save portability is made.

Snapshot APIs accept only the loaded core's exact state size and may service their coroutine job while the frontend is still restoring progress before Start. A failed upstream state-load callback is returned as failure; the worker retains and restores the previous snapshot. Save compatibility includes the core artifact hash, exact version, options, content identity and platform. Actual reset, cold resume, rejected-state rollback and long-running timing still require the final consolidated pass.

Cartridge byte-order handling is inherited from the pinned source. The library importer already distinguishes N64 cartridge formats. Disk Drive images and Transfer Pak companion assets are not declared supported by this initial package. No standalone manufacturer firmware is supplied; upstream PIF boot behavior uses its HLE implementation. Corresponding-source and binary content review remains necessary.

The Angrylion software profile is research-only and cannot receive distribution approval. Its related primary upstream retains a license prohibiting commercial product/activity use; the selected Mupen port lacks the component notice, so a parent GPL statement does not establish component permission. This is not a conclusion that the exact port has been conclusively licensed under that related text. A separately reviewed product renderer and corresponding-source inputs remain required. The packager rejects approval for this research profile independently of receipt contents. See [the upstream license](https://github.com/ata4/angrylion-rdp-plus/blob/master/MAME%20License.txt) and `security/retro-provenance-review.json`. No runtime binary has been built or admitted, and no compatibility/performance result exists.

A distinct GLideN64/HLE product candidate and native OpenGL adapter are now authored. Its prepared tree excludes Angrylion, CXD4 and parallel backends, while retaining the common save/identity adaptations. Full compiled dependency/compatibility review remains required. See `N64_OPENGL_RUNTIME.md`; the research profile has not been cleared or substituted into release scope.
