# Local performance measurements

The web-runtime measurement collector is authored but has not been run. A user can start it explicitly during an actual game. It collects no samples automatically. It waits for ten seconds of warm-up, then observes at least 120 seconds of uninterrupted play. Pause, visibility-driven suspension, a changed nominal game clock, invalid samples or an excessive capture duration cancel the incomplete run. No cancelled run is committed as a successful result.

The isolated worker timestamps libretro frame scheduling with its monotonic performance clock. Optional raw intervals are transferred only during an active capture. Emulated frame count, presented frame count and dropped scheduling slots are distinct; Battery mode's 30 Hz presentation limit is not reported as 60 rendered FPS. The audio worklet supplies actual starvation events. The core does not fill in unavailable GPU utilization, temperature, input-to-photon latency, battery savings or native driver counters.

The Rust service validates bounded samples and their observed duration, calculates quantiles from the pooled intervals and stores an immutable local report alongside exact game, core build and configuration hashes. It retains at most twenty reports per browser profile. Reports can be viewed, individually deleted and explicitly exported through the native file picker. There is no performance-report cloud upload. The database marks the device class unclassified, source as a worker performance clock and independent attestation false. Renderer-provided measurements are not silently admitted as trusted device-lab evidence by the game router.

The local comparison function requires matching game content, runtime family, platform, nominal clock and measurement origin. It retains both report identities and preset/build/config details and explicitly marks the comparison uncontrolled. A percent change between two interactive sessions does not establish that a configuration change caused an improvement. Repeatable input traces, fixed scenes, device/driver inventories, power/thermal probes, hardware latency and controlled A/B runs remain required for the full compatibility and performance lab.

An additional native collector is authored in `engines/native/src/measurement.cpp`. Its worker advertises measurement protocol 1; the admitted runtime also needs the `performance_measurement` capability, which is removed if the worker lacks that handshake. The desktop UI starts a capture explicitly and resumes/requests focus for the native game window. Ten seconds of actual frame-driven warm-up precedes 120 seconds of uninterrupted frame-completion intervals. Focus loss, hiding/minimization, pause, save/load/disc operations, timing changes and shutdown cancel an unfinished capture. The UI defers periodic autosave until capture ends. No capture is started by opening a game or by telemetry settings.

The native monotonic clock records completed frontend `retro_run` calls. In the shared historical schema these occupy `frames_emulated`; the native UI identifies their rate as core ticks per second because a frontend call does not establish a physical displayed frame or a universal guest-frame boundary. Successful presentations, dropped scheduling slots and post-priming audio-starvation episodes have separate counters. Metrics-window resets do not reset these capture totals. Gaps above five seconds, insufficient frames, changed nominal clock, more than 36,000 samples or an excessive duration invalidate the run. GPU timestamps, scanout, decoder latency, power and thermal values are not inferred.

Native raw intervals travel as bounded binary float64 little-endian bytes, rather than overflowing the worker's 64 KiB JSON frame. The native channel permits at most 288,000 bytes for this response and no binary payload on status/control replies. The Rust adapter checks the run ID, counters, duration, encoding, exact byte count and finite intervals. Game content, runtime pin/version, a hash of the complete artifact inventory and configuration including session/presentation policy come from the broker-owned session. The renderer cannot submit a native origin selector. Native records use `native_frontend_steady_clock`, `unclassified` and independent attestation false; the web submission endpoint always uses `web_worker_performance_clock`.

The session manager commits a completed native capture once, caches only its summary and retries storage only if the original commit failed. Repeated polling cannot reinsert a report after explicit deletion or retention. The same twenty-report profile limit and native-picked export apply. The native and web origins cannot be compared as though they used the same clock. The contained child is still an untrusted measurement source, so these interactive records do not become authenticated device-lab benchmark evidence for runtime ranking.

No benchmark result, pass rate, battery gain or release performance claim exists yet. This source is reserved for the single consolidated verification after the full implementation is authored.

On-demand native device inventory now has source for bounded Windows memory/power/DXGI data, Linux fixed proc/sysfs attributes, Apple memory/kernel sysctls and Android/iOS public-framework power/thermal augmentation. It is displayed separately from measured performance and does not enter stored benchmark identity, trust, ranking or a claimed controlled environment. Collection has not been executed. See `DEVICE_INFORMATION.md` for exact fields, unknowns, privacy, worker/cache limits and the remaining active-adapter/device-lab work.
