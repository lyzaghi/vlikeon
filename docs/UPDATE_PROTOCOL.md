# Desktop update implementation

Current item-14 changes and remaining implementation are tracked in
`ITEM14_INSTALL_REPAIR_UPDATES.md`. Extraction now observes cancellation during
bounded copies and before publication. The CLI adds `verify <release UUID>`;
entry/full-inventory checks reject intermediate links/reparse points. Fresh
installation floors use the current core schema constant rather than the older
schema numbers in the historical description below. No update operation ran.

The authored updater uses a private OmniPlay protocol, not a claim of TUF conformance. Its threat model includes hostile mirrors, interrupted downloads, stale signed metadata, conflicting release metadata, path traversal, archive amplification and accidental entry-point corruption. A fully compromised current OS user can replace that user's launcher and installation database; a per-user installer cannot protect itself against that adversary.

`platform/core/src/updates.rs` authenticates exact payload bytes with distinct Ed25519 threshold keys, verifies channel/platform, monotonic metadata versions, expiry, security epoch, schema compatibility and artifact hash/length. Consecutive root rotations require both old and new thresholds on identical payloads. Expired intermediate roots may authenticate a successor, but the final root and release must be fresh for any new installation. A remembered wall-clock high-water mark rejects large backward clock changes. Online compromise of one HTTPS mirror does not confer a signing key.

`platform/updater` embeds its channel policy at compilation with `OMNIPLAY_UPDATE_CHANNEL_JSON`. The checked-in development policy is disabled and has no trust keys. No web message, mutable runtime environment variable or command-line URL may override the release endpoint or trust root. An optional versioned root URL template supports automatic root recovery, limited to 32 consecutive rotations per attempt. An omitted or withheld successor cannot make an expired final root acceptable.

Signed metadata identifies a bounded OPPK0001 artifact. The artifact contains a JSON file inventory followed by uncompressed file bytes in inventory order. Extraction creates a fresh private staging directory, rejects links, special files, device names, duplicate case-insensitive names and file/directory collisions, validates every byte count and checksum and flushes files before publication. It never overwrites files in an existing release. Release packages require notices and a corresponding-source declaration; these declarations still require accurate release inventory and legal review.

An SQLite transaction selects the active immutable version directory. Existing browser processes keep their current executable files; the stable native-host launcher dispatches future connections to the activated version. The broker acknowledges health only after the real Game Hub connects and a real local profile opens. After three launches without that acknowledgement, the launcher can return to a previous installed version inside the security epoch. The metadata high-water mark never decreases during recovery. Profile data is never restored from an old binary package or silently downgraded.

The current authored profile schema is 10, including local favorites, save retirement and indexed history paging. New installation stores start with a schema floor of 10; existing installations use the broker's opened-schema notification/high-water update. Signed release metadata must declare a compatible schema interval, and a rollback cannot select an executable whose interval excludes the observed profile schema. No migration or rollback has been executed during authoring.

Game Hub exposes download, cancellation, explicit next-launch activation and explicit safe rollback through authenticated native messaging. Status responses omit filesystem paths and the potentially large package inventory. Download runs on a background worker with a 30-second idle receive bound and one-second cooperative cancellation polls that preserve the pending read future. Metadata/root requests are bounded separately. Extraction currently completes its current package operation before responding to cancellation. Activation rechecks installed file hashes. Launch rechecks executable entry points. Process creation and runtime loading still require platform verification in the final pass. Version/staging garbage collection and quota recovery remain outstanding.

The offline `omniplay-sign` utility creates private seeds only when its operator explicitly requests it, produces public key declarations, signs exact payload files and combines signatures on identical bytes. It never runs inside the Game Hub. Public production roots, publisher identities, expiry policy, signed repair releases, source archives and controlled HTTPS hosting must be supplied for a real release. No production or development signing secret has been generated while authoring this code.

`tools/install_user_release.ps1` authors the explicit Windows per-user bootstrap flow. It pins a user-supplied Authenticode publisher certificate and refuses to replace an existing stable bootstrap. Browser updates do not silently overwrite the bootstrap. A signed bootstrap maintenance mechanism, complete native installer/uninstaller UX, Linux package-manager integration and notarized macOS bundle/update handling remain required before desktop release. The custom package rejects symlinks, so a normal symlink-based macOS framework bundle needs its dedicated packaging path.

Reference used for threat analysis: [The Update Framework specification](https://theupdateframework.github.io/specification/v1.0.36/). All implementation, recovery, platform signing and attack cases remain unexecuted until the user's single final consolidated verification.
